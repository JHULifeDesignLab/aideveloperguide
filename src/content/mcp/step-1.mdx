## Goal
Understand the problem MCP solves and its architecture well enough to explain both in an interview — before touching any code.

---

## The problem: N×M integrations

An LLM is text-in, text-out. To *do* anything — read a file, query a database, send a message — something must connect it to that system. Before MCP, every AI application built custom connections to every data source it needed: N apps × M systems = N×M pieces of glue code, each different, none reusable.

MCP collapses that to N+M: each app implements the protocol once, each system gets one server, and everything interoperates. This is the same move USB made for hardware — hence the nickname.

---

## The architecture: host, client, server

Three roles, worth keeping straight because job postings use these words:

- **Host** — the AI application the user interacts with (Claude Code, Claude Desktop, Cursor, your own agent)
- **Client** — the connector inside the host that speaks the protocol (you mostly never see it)
- **Server** — a small program that exposes some capability: a filesystem, a Postgres database, GitHub, a weather API

The host asks the server what it offers, the model decides when to use it, and the server does the actual work. The model never touches your database directly — it asks the server, and the server decides what's allowed.

---

## What a server can offer

Three kinds of capability, and the distinction matters when you build one in Step 3:

1. **Tools** — actions the model can invoke: `query_database`, `create_issue`, `send_email`. This is the "give the LLM hands" part from the [agents overview](/aideveloperguide/agents).
2. **Resources** — data the host can read into context: file contents, schemas, documents.
3. **Prompts** — reusable prompt templates the server provides for common operations.
