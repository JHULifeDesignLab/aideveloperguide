## About
Render hosts the things Vercel's serverless model can't: persistent backend servers, databases, background workers, and scheduled jobs — the other half of a real application. You connect a GitHub repository, tell Render how to start your app, and it builds and runs it on every push.

If Vercel is "ship the frontend," Render is "run the backend." A FastAPI server for your RAG pipeline, an Express API, a Postgres database — this is where they live, with a workflow simple enough to learn in an afternoon.

## What you'll accomplish

- **Deploy a real backend** — a Python or Node API server running from your GitHub repo, redeployed on every push
- **Go full stack** — attach a Postgres database, host the frontend, manage secrets, and schedule recurring jobs
- **Build production habits** — health checks, log reading, and the platform judgment interviewers actually probe

## Why Render specifically?

Because it runs *processes*, not just functions. Your server starts and stays running — websockets work, long jobs work, in-memory state works. That's the mental model most CS coursework assumes, so there's less translation between "it works locally" and "it works deployed."

It's also the natural second platform after Vercel: pairing the two teaches you the frontend/backend split as it actually exists in industry, and being able to explain *which piece went where and why* is a genuinely strong interview answer.

## How this guide works

1. **Step 1 – Your First Web Service:** Deploy an API server from GitHub and understand free-tier spin-down behavior.
2. **Step 2 – Going Full Stack:** Postgres, static frontends, environment groups, and cron jobs.
3. **Step 3 – Production Habits:** Health checks, logs, scaling, and honest comparisons with the other platforms.
